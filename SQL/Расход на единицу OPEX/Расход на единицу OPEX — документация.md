## 3. Схема связей

В модели Qlik таблицы связаны через ключ `%КХЕ`. Расчётные таблицы собираются через ApplyMap, а не через JOIN:

```
DIM_КХЕ (%КХЕ)
    ├─ RPU_LONG       (%КХЕ)   помесячная витрина в длинном формате
    ├─ RPU_6M         (%КХЕ)   сравнение П1/П2
    ├─ TRIPS          (%КХЕ)   командировки
    ├─ TMZ_WRITEOFF   (%КХЕ)   списание ТМЗ
    ├─ FACT_KPI       (%KEY_KHE_PERIOD) ── FACT_OPEX (%KEY_KHE_PERIOD)
    │                                       └─ LEFT JOIN OPEX_CLASS_MAP ON КХЕ + Код статьи

Промежуточный расчёт RPU (удаляется из модели):
FACT_KPI (количества, амортизация)
    ├─ ApplyMap MAP_METRIC   ON КХЕ|Показатель  → Метрика
    ├─ ApplyMap MAP_AMORT    ON КХЕ|Месяц       → Амортизация
    ├─ ApplyMap MAP_OPEX_*   ON КХЕ|Месяц       → суммы по классам (17 мапов)
    └─ ApplyMap MAP_OPEX_TOTAL / DOSTAVKA       → Всего OPEX / Доставка АТМ
```

Проверьте в модели связь `FACT_KPI` ↔ `DIM_КХЕ`: у `FACT_KPI` и `FACT_OPEX` нет поля `%КХЕ`, есть только `%KEY_KHE_PERIOD`.

## 4. Структура данных

**Часть 1: FACT_KPI (количественные показатели и амортизация)**
- **Источник:** QVD и Excel из п. 1–10; каждый блок агрегируется до уровня Год × Месяц × КХЕ.
- **Фильтры:** `Год >= 2025` и `ДатаСортировки < MonthStart(Today())`. В отчёт попадают только закрытые месяцы.
- **Признак:** `Показатель` — например, Кол-во АТМ, Кол-во банкнот, Пробег или Амортизация.

**Часть 2: FACT_OPEX (проводки)**
- **Источник:** `проводки.xlsx`
- **Фильтры:** дата документа не раньше 2025 года; КХЕ из списка 501, 502, 503, 902, 1120, 1140, 1160, 1240, 1245, 1250, 1270, 1300, 1320.
- **Связи:** LEFT JOIN со справочником классов по паре КХЕ + код статьи.
- **Признак:** `Класс расходов` — правила в разделе 6.

**Часть 3: RPU (помесячный расчёт, промежуточная таблица)**
- Строится по `FACT_KPI`, из которого исключается амортизация. Остаются только пары КХЕ|Показатель, у которых есть метрика в `MAP_METRIC`.
- К каждой строке через ApplyMap подтягиваются амортизация, Всего OPEX и суммы по каждому классу.
- Считаются `Расход на единицу` и `% изменения RPU` (месяц к месяцу через Peek).

**Часть 4: RPU_LONG (витрина помесячного отчёта)**
- Строится только по основной метрике КХЕ (`MAP_PRIMARY_METRIC`), разворачивается по статьям из `LAYOUT`.
- К статьям добавляются три служебные строки: количество (порядок 90), «Расход на единицу» (91) и «%» (92).
- Порядок сортировки задают Dual-значения. Одинаковые названия статей в разных КХЕ различаются добавленными неразрывными пробелами (Chr(160)).

**Часть 5: RPU_6M (сравнение двух периодов по примеру заказчика)**
- **П2:** с начала года последнего закрытого месяца по этот месяц включительно (YTD).
- **П1:** тот же отрезок годом ранее.
- **Строки:** «Расход на единицу» (1), «Среднее кол-во — …» (2), статьи на единицу (10 + порядок статьи).
- **Знаменатель:** среднее помесячное количество за период (`Avg`).

**Часть 6: TRIPS** — детальный список командировок с 2025 года. КХЕ 1245 переводится в 1240.

**Часть 7: TMZ_WRITEOFF** — списание ТМЗ из Oracle с 2025 года. КХЕ определяется по группе ТМЗ (справочник SPR), батареи и аккумуляторы объединяются в номенклатуру «АКБ», считается флаг «Период к Периоду».

**Часть 8: DIM_КХЕ** — справочник КХЕ: код, наименование и полное название. Собирается из всех фактов, в том числе из RPU, иначе КХЕ 1245 не попадёт в справочник.

## 6. Бизнес-логика

### Формула «Расход на единицу»

| Метрика | Формула |
|---------|---------|
| Расход на 1 конверт (1140) | `(Аморт + OPEX) / (Кол-во / 2)` — одна отправка конверта состоит из двух отправок (конверт и уведомление) |
| Расход на охрану 1 объекта (1240) | `(Аморт + OPEX − Охрана ПЦН) / Кол-во объектов` |
| Расход на охрану 1 АТМ (1245) | `Охрана ПЦН / Кол-во АТМ` |
| Остальные метрики | `(Аморт + OPEX) / Кол-во` |

Если знаменатель ≤ 0, значение = NULL.

### Объединение КХЕ 1240 и 1245 (охрана)
- В фактах (`FACT_OPEX`, амортизация, `TRIPS`) КХЕ 1245 заменяется на 1240: эталонный расход 1240 — это сумма 1240 и 1245.
- В витрине RPU метрика «Расход на охрану 1 АТМ» показывается отдельной КХЕ 1245 и включает только ПЦН.

## 7. Примечания

- **Период данных:** с 01.2025 по последний закрытый месяц. Текущий месяц отсекается.
- **Поездки 1250:** `QVD_Incash_20250101.qvd` не обновляется (данные только по июнь 2026). Нужно решить, перегенерировать QVD или брать данные из StarRocks `BI.F$INCASH_DEP`.
- **Нет данных по 502 (POS):** количество POS не загружается, поэтому метрика «Расход на 1 POS» в RPU не появляется.
- **Период RPU_6M:** в комментариях скрипта написано «6 последних закрытых месяцев», но код считает с начала года (YTD) и сравнивает с тем же периодом прошлого года. Переменная `v6M_Offset = 12` объявлена, но в расчётах не используется.
- **Открытый вопрос к заказчику:** КХЕ 1245, статьи «1» и 2603 сейчас попадают в «Прочие». Нужно решить, оставить их там или перенести в «Тех охрану».
- **Причины изменений (`Причина 6M`):** поле пустое. Нужен лист «Причины» (КХЕ, Метрика, Статья, Причина) и MAP_REASON.
- **Подключения:** `DWH OLE DB` идёт под личной учёткой hq_urymbayev_28583, lib `amortizacia_2025` — под hq_tolybayev_59417. Если у этих сотрудников отзовут права, отчёт перестанет загружаться.
- **Ручные источники:** Ручники, амортизация 2025 и проводки — это Excel-файлы, их нужно обновлять вручную каждый месяц.
- **Важно для скрипта:** при загрузке `KOL_1240` обязателен `NoConcatenate`. Без него таблица автоматически склеится с `KOL_MANUAL` и загрузка упадёт.
