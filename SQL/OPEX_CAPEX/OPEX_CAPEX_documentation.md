# Документация отчёта: OPEX / CAPEX (расходы ДБУ и капитальные затраты)

## 1. Шапка (мета-информация)

| Поле | Описание |

## 3. Схема связей

Отчёт строится из двух независимых Oracle-подзапросов (для факта OPEX и для сверки со сметой/заявками), плюс отдельного `select *` для CAPEX. Остальные таблицы (справочники) не объединяются оператором `JOIN`, а ассоциируются в модели Qlik автоматически по одноимённым ключевым полям.

**a) Источник факта OPEX (`OPEXtemp`):**

```
BI.F$ALLOC_PAYMENT_DOCS_VW (apdv)
    └─ JOIN BI.F$SPR_CODE_EXPENSE_IBSO_V (c)  ON apdv.PDIBSO_EXPENSE_ID = c.ID
```

**b) Источник сметы/заявок (используется одинаково в `SmetaOpex` — трижды, в ветках SMETSUM / SMETSUM2 / PAYSUM — и в `SmetaCapex`):**

```
S06.Z#KAS_REQUEST_PAY (A1)
    ├─ JOIN S06.Z#PRODUCT (A2)        ON A1.ID = A2.ID
    │      └─ LEFT JOIN S06.Z#USER (A3)         ON A2.C_CREATE_USER = A3.ID
    ├─ JOIN S06.Z#TMC_DOG_LIST (B1)   ON B1.C_REQUEST_PAY = A1.ID
    └─ JOIN S06.Z#TMC_RASH_STATS (C1) ON C1.C_REQUEST_PAY_ARR = B1.COLLECTION_ID
           ├─ LEFT JOIN S06.Z#HOZED (C2)         ON C1.C_KXE = C2.ID         -- КХЕ счёта
           ├─ LEFT JOIN S06.Z#HOZED (C3)         ON C1.C_KXE_2 = C3.ID       -- КХЕ бюджета
           └─ LEFT JOIN S06.Z#SPR_CODE_EXPENSE (C4) ON C1.C_COSTS_CODE = C4.ID
```

**c) Ассоциации на уровне Qlik-модели (по совпадающим полям, без явного JOIN в SQL):**

```
OPEX ──[КХЕ]── SPRKXEOPEX / SPRKXECAPEX
     ──[FIL]── SPRFILOPEX
     ──[RentKey]── SPRRENT
     ──[RentKey→RKEY2]── RentSPR2
     ──[PRILKEY]── DKaspiService
     ──[DSKEY]── DSKaspiService
     ──[SMETKEY]── SmetaOpex
CAPEX ──[С_Хоз. ед-ца]── SPRKXECAPEX
      ──[СметОбъект]── SmetAdress
      ──[через SmetaCapex]── смета по заявкам (С_Номер документа / СметОбъект)
Командировки (RESIDENT OPEX) ── LEFT JOIN ── SPRKXEOPEX (по КХЕ) → экспорт в QVD
```

## 4. Структура данных

**Часть 1: OPEX — факт операционных расходов (проводки ДБУ)**
- **Источник:** `BI.F$ALLOC_PAYMENT_DOCS_VW` + `BI.F$SPR_CODE_EXPENSE_IBSO_V`
- **Связи:** join по `PDIBSO_EXPENSE_ID = ID` для получения наименования кода затрат
- **Фильтры:** `pdibso_rep_date >= '2022-01-01'`; `business_code` (КХЕ) — ограниченный список кодов подразделений; `pdibso_code_expense` — ограниченный список кодов затрат (~85 кодов); `BALANCE_ACCOUNT <> '5734'`; `pdibso_payment_details is not null`
- **Признак:** промежуточная таблица `OPEXtemp` обогащается вычисляемыми полями (см. раздел 5), затем переименовывается в `OPEX` (RESIDENT) и `OPEXtemp` удаляется (`DROP TABLE`)

**Часть 2: SmetaOpex — сверка факта со сметой по заявкам (аренда, ремонт и близкие коды затрат)**
- **Источник:** цепочка таблиц `S06.*` (см. схему связей, п. b)
- **Связи:** описаны в п. b выше
- **Фильтры:** `A1.STATE_ID = 'PAID'`; `A1.C_REQ_ID_1C is not null`; `A1.C_DOP_REC_1C is not null` (заявка должна содержать XML-блок со сметой из 1С); `C_COST_CODE IN ('2301','2303','2304','2850')`
- **Признак:** три ветки объединяются через `UNION`, помеченные полем `FROMW`:
  - `SMETSUM` — сумма сметы как есть (расхождение с фактическим платежом обязательно: `ROUND(C_ESTIMATE_SUM) <> ROUND(C_SUMMA2)`)
  - `SMETSUM2` — та же ветка, но сумма сметы дополнительно делится на 1.12 (пересчёт «с НДС» → «без НДС»)
  - `PAYSUM` — сумма сметы приравнивается к фактической сумме платежа (запасной вариант без фильтра на расхождение)
  - Внутри каждой ветки дедупликация по `SmetKey` = `Поставщик + Сумма сметы` (`RM = 1`, первый по дате заявки), затем по всему объединению — ещё раз дедупликация по `SmetKey` с выбором строки с максимальной `C_SUMMA2` (`RMM = 1`)

**Часть 3: CAPEX — факт капитальных расходов**
- **Источник:** `BI.F$DM_PAYMENT_DOC_IBSO_BB_QLIK_V` (`select *`, без явных фильтров и join в самом скрипте)
- **Связи:** нет SQL-джойнов; ассоциируется с другими таблицами модели в Qlik по `С_Хоз. ед-ца` (со справочником `SPRKXECAPEX`) и по `СметОбъект` (со справочниками смет и адресов)
- **Признак:** таблица содержит одновременно фактическую сумму платежа (`С_Сумма платежа`) и плановую (`С_План`) — сравнение план/факт заложено уже в источнике

**Часть 4 (сопутствующий блок): SmetaCapex — агрегированная смета по заявкам для CAPEX**
- **Источник:** та же цепочка `S06.*`, что и в части 2, но без UNION и без фильтра по коду затрат/расхождению
- **Связи:** идентичны п. b
- **Фильтры:** `STATE_ID = 'PAID'`; `C_REQ_ID_1C`, `C_DOP_REC_1C` не пустые
- **Признак:** агрегация `SUM(C_SUMMA2)` с группировкой по номеру заявки, назначению платежа, объекту и описанию — плановая сумма по заявке в разрезе объекта

**Часть 5 (производная выгрузка): Командировки**
- **Источник:** `RESIDENT OPEX`, фильтр `[O_Группа затрат] = 'Расходы на служебные командировки'`
- **Связи:** `LEFT JOIN` со справочником `SPRKXEOPEX` по полю `КХЕ` (добавляет укрупнённое подразделение `Lev1`/`Lev2`)
- **Фильтры:** только группа затрат «командировки»
- **Признак:** таблица не входит в итоговую модель приложения — сохраняется в `Командировки.qvd` и сразу удаляется из памяти (`DROP TABLE`); фактически это ETL-шаг для другого отчёта/приложения

## 5. Ключевые поля

### 5.1. Таблица OPEX (основные вычисляемые/нетривиальные поля)

| Поле | Описание |
|------|----------|
| `[O_Дата]` | Источник: `PDIBSO_REP_DATE`. Логика: `date(floor(...))` — дата проводки без времени |
| `[КХЕ]` | Источник: `BUSINESS_CODE`. Ключ для связи со справочниками подразделений |
| `RentKey` | Вычисляемое. Логика: `if([O_Группа затрат] like 'Аренда', UPPER(PRIL3 & DDD & SPLR3))` — составной ключ для сопоставления со справочником аренды `SPRRENT`, строится только для строк с группой затрат «Аренда» |
| `DDD` | Вычисляемое (в исходном SQL). Логика: извлечение номера и даты договора из текста `PDIBSO_PAYMENT_DETAILS` после маркера «Договор№» (маркер приводится к единому виду из вариантов написания: «договору №», «дог.№», «Дог.№» и т.д.) |
| `SPLR3` / `PRIL3` | Вычисляемые. Логика: очистка наименования поставщика от организационно-правовой формы (ИП/АО/ТОО/КХ) и извлечение номера приложения к договору из текста назначения платежа (маркер «прил.№») |
| `DSKEY` | Вычисляемое. Логика: `UPPER(DDD \|\| SPLR3)`, если `DDD` заполнен — ключ связи со справочником доп. соглашений `DSKaspiService` |
| `PRILKEY` | Вычисляемое. Логика: `PRIL3 & 'К' & UPPER(DDD)`, если заполнены оба, либо просто `DDD` — ключ связи со справочником договоров/приложений `DKaspiService` |
| `TripInf` | Вычисляемое (промежуточное). Логика: каскад `if(...like...)` с `TextBetween` по 6+ текстовым шаблонам назначения платежа (командировки по Казахстану, зарубежные командировки, суточные, системные списания BTMC.KZ) — извлекает «сырой» фрагмент с ФИО/направлением, только для группы затрат «Расходы на служебные командировки» |
| `[Сотрудник]` | Вычисляемое из `TripInf`. Логика: обрезка строки по первой скобке `(` либо по 2–3 слову, в зависимости от формата — выделяет ФИО сотрудника |
| `[Направление]` | Вычисляемое из `TripInf` и `[O_Назначение]`. Логика: если назначение похоже на начисление суточных → фиксированный текст «Начисление суточных»; иначе — текст в скобках либо последнее слово через `SubField`, с очисткой суффиксов «г.»/«c.» |
| `SMETKEY` | Вычисляемое. Логика: `if(WildMatch([O_Код затрат],'2301','2303','2304'), SPLR3 & Fabs(Round([O_Сумма])))` — ключ связи с таблицей `SmetaOpex` (поставщик + модуль суммы) |
| `[ПериодКПериоду]` | Вычисляемое. Логика: `if(year(MD)-year(PDIBSO_REP_DATE)<2 and Month(PDIBSO_REP_DATE)<=Month(Today())-1, 'Период к Периоду')` — флаг для сравнимых периодов (не более 2 лет от максимальной даты в наборе и завершённый месяц) |
| `ТекущийГод` | Вычисляемое. Логика: `if(year(today())=Year([O_Дата]),1,0)` — быстрый флаг «текущий год» |

### 5.2. Таблица SmetaOpex / SmetaCapex

| Поле | Описание |
|------|----------|
| `SmetKey` | Вычисляемое. Логика: `UPPER(SPLR2) \|\| Сумма_сметы` (или `Сумма_платежа` в ветке PAYSUM) — ключ дедупликации/связи |
| `C_SUMMA` | Вычисляемое. Логика НДС — см. раздел 6 |
| `C_ESTIMATE_SUM` | Источник: `DWH_SAN.STR_P.EXTRACT(A1.C_DOP_REC_1C,'<Amount>','</Amount>')` — сумма сметы, извлекается из XML-блока заявки; в ветке `SMETSUM2` дополнительно делится на 1.12 |
| `QOBG` | Вычисляемое. Логика: `COUNT(DISTINCT C_OBJECT) OVER (PARTITION BY SPLR2+сумма)` — количество разных объектов с одинаковым ключом (индикатор неоднозначности сопоставления) |

### 5.3. Таблица CAPEX (переименование источника, без сложной логики)

| Поле | Описание |
|------|----------|
| `[С_Хоз. ед-ца]` | Источник: `H_CODE`, с заменой `if(H_CODE='1240','1245',H_CODE)` — код 1240 принудительно переносится в 1245 |
| `[С_Сумма платежа]` / `[С_План]` | Источник: `C_SUMMA_PLAT` / `PLAN_SUM` — факт и план идут одной строкой из витрины, без вычислений в скрипте |

## 6. Бизнес-логика

**Логика расчёта НДС** (одинаковая в блоках `SmetaOpex` и `SmetaCapex`):

| Условие | Результат |
|---------|-----------|
| Код затрат НЕ начинается с `2850` И `C_NDS = '1'` | Сумма увеличивается на 12%: `(C_SUMMA/100)*112` |
| Код затрат начинается с `2850` ИЛИ `C_NDS ≠ '1'` | Сумма берётся как есть, без пересчёта |

**Правила извлечения контрактных ключей из текста назначения платежа** (поле `PDIBSO_PAYMENT_DETAILS`):
- Номер договора — после нормализации вариантов написания («договору №», «дог.№», «Дог.№», «пуб.договору» и т.п.) к единому маркеру «Договор№», с заменой точек на слэши в номере
- Номер приложения к договору — после нормализации вариантов («Приложение №», «прил.№», «прил. №» и т.п.) к маркеру «прил.№»
- Наименование поставщика — очищается от кавычек (включая «ёлочки») и апострофов, от организационно-правовой формы (ИП/АО/ТОО/КХ — берётся то, что после сокращения)

**Правила определения ключа аренды:** `RentKey` строится только для строк с группой затрат «Аренда»; используется для связи с внешним справочником `SPRRENT` (Excel) и с отчётом по действующим договорам аренды `RentSPR2` (QVD)

**Фильтр активности договоров аренды (`RentSPR2`):** тип собственности содержит «РЕНД» (аренда), период отчёта ≥ 2022-01-01, и либо срок действия договора не заполнен (`01.01.0001`), либо отчётный период не превышает дату окончания договора/пролонгации

**Дедупликация смет (`SmetaOpex`):** для каждого сочетания «поставщик + сумма» берётся первая по дате заявки строка внутри ветки (`RM=1`), а после объединения трёх веток (`SMETSUM`/`SMETSUM2`/`PAYSUM`) — строка с максимальной суммой по ключу (`RMM=1`); таким образом одной комбинации поставщик+сумма может соответствовать только одна запись сметы

**Распознавание командировочных расходов:** назначение платежа разбирается по 6 текстовым шаблонам (внутренние/зарубежные командировки, суточные, урегулирование излишне начисленной суммы, системные списания BTMC.KZ) для извлечения ФИО сотрудника и направления поездки — правило применяется только к строкам с группой затрат «Расходы на служебные командировки»

## 7. Примечания

- Промежуточная таблица `OPEXtemp` и производная таблица `Командировки` удаляются из памяти скрипта после использования (`DROP TABLE`) — в итоговой модели приложения из «расчётных» таблиц остаются только `OPEX`, `CAPEX`, `SmetaOpex`, `SmetaCapex` и справочники.
- Таблица `Командировки` не входит в модель этого приложения — она выгружается в отдельный файл `lib://QVD Tables/KaspiService/Командировки.qvd`, то есть служит источником для другого отчёта/приложения (следует обновлять этот скрипт согласованно с потребителем QVD).
- Справочники `SPRRENT`, `DKaspiService`, `DSKaspiService`, `SmetAdress` подгружаются из внешних Excel-файлов на файловом ресурсе `lib://kaspi_service (hq_samenov_55251)` — обновляются вручную/по регламенту вне Qlik-скрипта; при рассинхронизации связи по `RentKey`/`PRILKEY`/`DSKEY` перестают работать.
- `RentSPR2` читает уже готовый `RentSTR.qvd` — зависит от отдельного ETL-процесса отчёта по аренде, который должен обновляться заранее.
- Известное ограничение: сопоставление факта со сметой построено на текстовом парсинге назначения платежа и XML-полей заявки (`C_DOP_REC_1C`) — чувствительно к формату заполнения заявки в системе-источнике; при нестандартном тексте возможны пропуски или неверные сопоставления по `RentKey`/`DSKEY`/`PRILKEY`/`SMETKEY`.
- Связанные отчёты: отчёт по аренде (источник `RentSTR.qvd`), отчёт «Командировки» (потребитель выгружаемого QVD).
- Ссылка на BI-отчёт и точный тип коннекта (алиас подключения в Qlik) в исходном скрипте не заданы явно — уточнить у владельца приложения при заполнении шапки для публикации.
