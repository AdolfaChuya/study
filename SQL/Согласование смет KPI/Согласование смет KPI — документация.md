# Согласование смет KPI

Контроль сроков согласования смет по цепочке: менеджер строительства → НО → ДТО → ДИ. Отчёт состоит из двух частей:
- **TABLE_1** — документы со сроками и KPI каждого согласующего, признаком просрочки менеджера и общим временем согласования;
- **TABLE_2** — помесячная статистика по менеджерам: сколько смет обработано, сколько возвращено на доработку, значение KPI.

## 1. Шапка

| Поле | Описание |
|------|----------|
| **Коннект** | Starrocks (`staroks (BKS)`) |
| **Сложность** | Низкая |
| **Источники** | KASPI_PEOPLE (схема S0008) |
| **Ссылка** | — |

## 2. Источники данных

| № | Таблица / Представление | Схема | Назначение |
|----|------------------------|-------|------------|
| 1 | `GET_ESTIMATES_APPROVERD_ON_TIME` | `S0008` | Документы-сметы: даты и ФИО согласований на каждом этапе, плановые даты, время ответа, KPI |
| 2 | `GET_ESTIMATES_RETURNED_FOR_REVISION` | `S0008` | Помесячная сводка по менеджерам: всего смет, возвраты на доработку, KPI |

Содержимое обоих объектов формируется на стороне источника: в самом скрипте только `SELECT *` и переименование полей.

## 3. Схема связей

JOIN-ов нет, таблицы загружаются независимо:

```
TABLE_1  (Номер документа)       — уровень документа сметы
TABLE_2  (MANAGERNAME + MONTH + YEAR) — уровень менеджера и месяца
```

Общих полей нет: в `TABLE_1` менеджер называется `Менеджер`, в `TABLE_2` — `MANAGERNAME`. Автоматической связи в модели Qlik нет.

## 4. Структура данных

**Часть 1: TABLE_1 — документы согласования смет**
- **Источник:** `S0008.GET_ESTIMATES_APPROVERD_ON_TIME` (все строки без фильтров).
- **Гранулярность:** один документ (смета) на строку.
- **Содержание:**
  - статус и даты документа (создание, принятие, проводка);
  - этапы согласования: менеджер → НО → ДТО → ДИ — по каждому дата согласования, ФИО, дата отклонения, плановая дата и время ответа;
  - KPI по НО, ДТО и ДИ;
  - общее время согласования в днях и КХЕ подразделения.
- **Вычисляемые поля:** `Просрочка` и `Просрочка время` (раздел 6).

**Часть 2: TABLE_2 — возвраты на доработку по менеджерам**
- **Источник:** `S0008.GET_ESTIMATES_RETURNED_FOR_REVISION` + вычисляемое поле `STATUS_EMP`.
- **Гранулярность:** менеджер × месяц × год.
- **Содержание:** общее число смет, число возвратов на доработку, KPI.
- **Признак:** `STATUS_EMP` — «Уволен», если в имени менеджера есть суффикс `_уволен`, иначе «Действующий».

## 6. Бизнес-логика

### Просрочка менеджера (TABLE_1)

| Условие | `Просрочка` | `Просрочка время` |
|---------|-------------|-------------------|
| `Дата согласования менеджером − Плановая дата менеджера > 0` | Да | Эта разница |
| Иначе (в срок, раньше срока, любая из дат пуста) | Нет | 0 |

### Статус сотрудника (TABLE_2)

| Условие | `STATUS_EMP` |
|---------|--------------|
| `MANAGERNAME` оканчивается на `_уволен` | Уволен |
| Иначе | Действующий |

### Преобразование месяца (TABLE_2)
`Month(Date#(MONTH, 'M'))` превращает номер месяца в название месяца (например, 3 → «Мар»), поле остаётся с тем же именем `MONTH`.

## 7. Примечания

- **Просрочка считается только для менеджера.** Для НО, ДТО и ДИ есть плановые даты и KPI, но признака просрочки в скрипте нет, он считается в источнике (поля KPI) или в интерфейсе.
- **Несогласованные документы не считаются просроченными.** Если `Дата согласования менеджером` пуста, разность пуста, и признак получает значение «Нет», даже если плановая дата уже прошла.
- **Единица измерения `Просрочка время`.** Разность дат даёт значение в днях (с долями, если даты содержат время). Формат нужно проверить в источнике.
- **Нет связи между таблицами.** `TABLE_1` и `TABLE_2` связаны только по смыслу (менеджер), общих полей нет. Для связи нужно переименовать `Менеджер` или `MANAGERNAME` и привести написание ФИО к одному виду. В `TABLE_2` у уволенных менеджеров в имени есть суффикс `_уволен`, в `TABLE_1` такого суффикса может не быть.
- **Опечатка в названии источника:** `GET_ESTIMATES_APPROVERD_ON_TIME` (`APPROVERD`). Это имя самого объекта в БД, при его переименовании скрипт нужно обновить.
- **Логика KPI и плановых дат** считается внутри `GET_ESTIMATES_*` на стороне БД, в скрипте её нет. Формулы нужно уточнять у владельца этих объектов.
- **Обе загрузки — полные, без фильтров по периоду.** Инкрементальной загрузки нет.
