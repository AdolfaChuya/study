# Документация отчёта: Договора аренды с % изм.

## 1. Шапка (мета-информация)

| **Источники** | `S0115` (реестр банковских помещений `BANK_PREMISES` с историей договоров аренды в JSON) |

## 2. Источники данных

| № | Таблица / Представление | Схема | Назначение |
|----|------------------------|-------|------------|
| 1 | `BANK_PREMISES` | `S0115` | Единственный источник отчёта — реестр банковских помещений; история изменений условий аренды хранится в колонке `JSON_BODY` как вложенный массив `agreements.agreement`, который разворачивается в строки |

## 3. Схема связей

Классических JOIN-ов между таблицами нет — используется только `LEFT OUTER JOIN LATERAL unnest(...)` для разворота JSON-массива внутри одной и той же записи `BANK_PREMISES` (каждое помещение может содержать несколько версий договора аренды):

```
S0115.BANK_PREMISES (A)
    └─ LEFT OUTER JOIN LATERAL unnest(JSON_BODY->'agreements.agreement') a(pr) ON TRUE
           -- разворачивает JSON-массив договоров/допсоглашений в отдельные строки
```

---

## 4. Структура данных

Отчёт состоит из одной логической части, построенной как три вложенных друг в друга подзапроса (без `UNION ALL`):

**Часть 1 (внутренний слой): разбор JSON-массива договоров**
- **Источник:** `S0115.BANK_PREMISES`, разворот массива `JSON_BODY->'agreements.agreement'` через `LATERAL unnest`
- **Связи:** `LEFT OUTER JOIN LATERAL ... ON TRUE` — технический разворот JSON, а не связь между разными таблицами
- **Фильтры:** `currentAmount IS NOT NULL AND currentAmount <> 0` — исключаются записи без суммы аренды или с нулевой суммой (расторгнутые/пустые договоры)
- **Признак:** каждое поле договора извлекается из JSON через `get_json_string(a.pr, '$.<поле>')`; `DISTINCT` на этом уровне убирает полные дубликаты строк

**Часть 2 (средний слой): нормализация периода**
- **Источник:** результат части 1
- **Связи:** нет (обёртка над предыдущим слоем)
- **Фильтры:** нет дополнительных
- **Признак:** `PERIOD` приводится к первому числу месяца — `CAST(DATE_FORMAT(PERIOD, '%Y-%m-%01') AS DATE)`; сортировка `ORDER BY PERIOD, AMOUNTCHANGECOUNT, EFFECTIVEDATE`

**Часть 3 (внешний слой): дедупликация до одной записи на месяц/арендатора**
- **Источник:** результат части 2
- **Связи:** нет
- **Фильтры:** `WHERE RN = 1`
- **Признак:** `ROW_NUMBER() OVER (PARTITION BY PERIOD, COUNTERAGENTIIN ORDER BY PERIOD, COUNTERAGENTIIN, AMOUNTCHANGECOUNT, EFFECTIVEDATE) AS RN` — в каждом периоде (месяце) для каждого арендатора (по ИИН) остаётся только одна запись — с наименьшим `AMOUNTCHANGECOUNT` и самой ранней `EFFECTIVEDATE` (см. риск в разделе 7)

## 5. Ключевые поля

| Поле | Описание |
|------|----------|
| `PERIOD` | Источник: `period` (JSON `$.period`). Логика: приведение к дате и нормализация к первому числу месяца |
| `EFFECTIVEDATE` | Источник: JSON `$.effectiveDate` — дата вступления в силу конкретной версии договора/допсоглашения |
| `COUNTERAGENT` / `COUNTERAGENTIIN` | Источник: JSON `$.counteragent` / `$.counteragentIin` — наименование и ИИН арендодателя/арендатора; `COUNTERAGENTIIN` используется как ключ дедупликации |

| `ISNDS` | Источник: JSON `$.isNDS` — признак «сумма с НДС» |
| `AMOUNTCHANGECOUNT` | Источник: JSON `$.amountChangeCount` — порядковый номер изменения суммы аренды (версия допсоглашения по сумме); участвует в сортировке для дедупликации |
| `MONTHAMOUNT` / `MONTHAMOUNTNONDS` | Источник: JSON `$.monthAmount` / `$.monthAmountNoNDS` — сумма аренды в месяц (с НДС / без НДС) |
| `CURRENTAMOUNT` | Источник: JSON `$.currentAmount`. Логика: фильтр — не NULL и не 0 |
| `SQMETERPRICE` | Источник: JSON `$.sqMeterPrice` — цена за квадратный метр |
| `BRANCHOFFICE` | Источник: JSON `$.branchOffice` — филиал/точка |
| `ROOMTYPE` | Источник: JSON `$.roomType` — тип помещения |
| `DECRYPTION` | Источник: JSON `$.decryption` — расшифровка/описание |
| `OWNERSHIPTYPE` | Источник: JSON `$.ownershipType` — тип собственности (аренда/собственное и т.п.) |
| `AREA` / `STAFFAREA` | Источник: JSON `$.area` / `$.staffArea` — общая площадь и площадь под персонал |
| `FIXPRICETERM` | Источник: JSON `$.fixPriceTerm` — срок фиксации цены |
| `MAXRISEPERCENT` | Источник: JSON `$.maxRisePercent` — максимальный процент повышения арендной ставки (ключевое поле для «% изм.» в названии отчёта) |
| `UTILITIES` | Источник: JSON `$.utilities` — включены ли коммунальные платежи |
| `DIVISIONCODE` / `DIVISIONNAME` | Источник: JSON `$.divisionCode` / `$.divisionName` — код и название подразделения-арендатора |

| `EMPLOYEENUM` | Источник: JSON `$.employeeNum` — количество сотрудников в помещении |

## 6. Бизнес-логика

**Правило отбора одной записи на период/арендатора:** для каждой пары «месяц (PERIOD) + арендатор (COUNTERAGENTIIN)» может существовать несколько версий условий договора (разные `AMOUNTCHANGECOUNT`/`EFFECTIVEDATE`, например при изменении ставки в течение месяца); отчёт берёт **только первую по порядку** версию (`RN = 1` после сортировки по `AMOUNTCHANGECOUNT`, `EFFECTIVEDATE`) — то есть самое раннее изменение в месяце, а не итоговое/последнее.

**Правило включения записи в отчёт:** договор попадает в отчёт только если сумма текущей аренды (`currentAmount`) заполнена и не равна нулю — договоры без суммы или с обнулённой суммой (например, расторгнутые) не учитываются.

**Нормализация периода:** отчётный период всегда приводится к первому числу месяца, независимо от того, какой день месяца был указан в исходных данных JSON — это обеспечивает единый ключ для помесячной агрегации/сравнения.

## 7. Примечания

- **Потенциальный риск (важно проверить с владельцем отчёта):** дедупликация оставляет запись с **наименьшим** `AMOUNTCHANGECOUNT` и **самой ранней** `EFFECTIVEDATE` в периоде (`ORDER BY ... ASC` + `RN = 1`). Если бизнес-цель отчёта — показать **актуальные на конец месяца** условия аренды (в т.ч. процент повышения ставки), то нужна **последняя** версия изменения за период, а не первая. Рекомендуется уточнить, было ли выбрано `RN = 1` по возрастанию осознанно, либо нужно `ORDER BY ... DESC` для получения последнего изменения в месяце.
- Отчёт полностью зависит от структуры JSON-поля `JSON_BODY` в `S0115.BANK_PREMISES`, конкретно от пути `agreements.agreement` и вложенных ключей (`period`, `effectiveDate`, `counteragentIin` и т.д.). Изменение структуры JSON на стороне источника (переименование/удаление ключей) приведёт к NULL-значениям без явной ошибки скрипта.
- Помещение без единого статичного arenda-договора, но с несколькими элементами массива `agreements.agreement`, порождает несколько строк на входе — до дедупликации это нормальное поведение (история изменений), после дедупликации остаётся одна строка на месяц на арендатора.
- Название отчёта («с % изм.») указывает на то, что ключевая аналитическая метрика — `MAXRISEPERCENT` (максимально допустимый процент повышения арендной ставки); при доработках отчёта имеет смысл проверить, не требуется ли также поле фактического процента изменения ставки между периодами (сейчас в источнике нет отдельного поля «факт изменения %», только предельно допустимый процент).
- Связанные отчёты: пересекается по смыслу с отчётом по амортизации/арендным объектам (`SPRRENT`, `RentSPR2` в OPEX/CAPEX) — оба используют понятие ставки и договора аренды, но из разных источников (Excel/QVD там, JSON-витрина `S0115` здесь); при сведении данных возможны расхождения в перечне активных договоров.
