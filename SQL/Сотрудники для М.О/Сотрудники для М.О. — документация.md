# Сотрудники для М.О.

Список сотрудников Kaspi.kz отдельных должностей (рабочие и инженерные профессии, инкассаторы, водители, отдельные руководители) с профессиональной вредностью по каждой должности и датой последнего медосмотра. По составу полей М.О., вероятно, означает «медосмотр», но в скрипте это не сказано.

Что войдёт в итоговую модель:
- **KASPI_EMP** — отобранные сотрудники: ФИО, ИИН, должность, подразделение (до 8 уровней), город, дата приёма, пол, дата рождения, профессиональная вредность;
- **STATUS_FINAL** — стаж сотрудника (общий и в текущей должности);
- **LAST_MED** — дата последнего медосмотра по табельному номеру;
- **MasterCalendar** — календарь с флагами выходных, концов месяцев и недель.

Бо́льшая часть скрипта (разбор приёмов, переводов, увольнений) нужна только для расчёта стажа. Остальные результаты этой части в конце удаляются (раздел 7).

## 3. Схема связей

```
Расчёт стажа (STATUS_FINAL):
S0008$STAFOPERDATA → STATUS_START_END (периоды работы)
    ├─ исправление пересечений: по сотруднику (UNIID, логика Kaspi.kz) и по компании (CORPID)
    ├─ LEFT JOIN DEPARTMENTS (уровни 1–7)  ON IDDEP
    └─ LEFT JOIN POSITIONS                  ON IDPOS
    → события: приём / перевод / увольнение → периоды (STATUS)
    → STATUS_FINAL (общий стаж, стаж в должности) — только последний период по STATUS_IDEMPL

Справочник сотрудников (KASPI_EMP):
STATUS.qvd (срез на сегодня − 2)
    ├─ LEFT JOIN S0008.EMPLOYEES + USERS_POSITIONS  ON KEY_FIO (ФИО без пробелов, верхний регистр)
    ├─ LEFT JOIN DEPARTMENTS + HR_DEPARTMENT_CITY_V ON IDDEP
    │
    ├─ Группа A  KASPI_EMP_FILTERED — отбор по названию должности и подразделению
    │       └─ LEFT JOIN INLINE (вредность)  ON POSITION_KEY
    ├─ Группа B  KASPI_EMP_NESTED — все сотрудники
    │       └─ INNER JOIN «Новые позиции для отчёта.xlsx»  ON ID (ID должности) → вредность
    └─ CONCATENATE (A + B) → итоговая KASPI_EMP

Итоговая модель Qlik:
KASPI_EMP ── STATUS_IDEMPL ── STATUS_FINAL
KASPI_EMP ── STATUS_TABNO  ── LAST_MED
MasterCalendar (Дата) — с остальными таблицами не связан
```

## 4. Структура данных

**Часть 1: MasterCalendar**
- Диапазон: с 01.01.2010 по вчера.
- Выходные дни: `LEFT JOIN` с `HR_CALENDAR_V` (дни с `IS_DAY_OFF_FLG = 'Y'`), поле `Выходной` = '1' для выходных.
- Флаги «Конец месяца» и «Конец недели»: 1 для последнего дня месяца или недели, а также для вчерашнего дня (последняя дата календаря).

**Часть 2: Кадровые периоды — расчёт стажа**
- **Источник:** `DWH_STAGE2.S0008$STAFOPERDATA`. Все записи загружаются как «Штат».
- **Шаги:**
  1. Из операций строятся периоды работы: начало — дата операции, конец — день перед следующей операцией (при увольнении конца нет).
  2. Периоды сортируются и сшиваются отдельно для сотрудника целиком (логика «Kaspi.kz») и для каждой компании (логика «Каждое АО/ТОО отдельно»). Правила — в разделе 6.
  3. К периодам добавляются уровни подразделения и должность.
  4. Из периодов определяются события: приём, перевод, увольнение.
  5. События сворачиваются обратно в периоды.
  6. Для каждого сотрудника (`STATUS_IDEMPL`) оставляется последний период и по нему считается стаж.
- **Результат:** таблица `STATUS_FINAL` с полями `STATUS_IDEMPL`, `STATUS_HIRE_DATE`, `Общий стаж`, `Стаж в должности`.

**Часть 3: Исходный список сотрудников (до отбора)**
- **Источник:** `STATUS.qvd`, снимок на дату «сегодня − 2 дня» (поле `Дата`).
- **Фильтры:** тип записи — «действующий», «длительное отсутствие» или «переходный период»; тип контракта «Штат»; тип логики «Kaspi.kz».
- **Обогащение:**
  - должность, ID должности и табельный номер из `S0008.EMPLOYEES` по ФИО (последняя запись по дате приёма среди тех, кто не уволен или был принят повторно);
  - иерархия подразделения (8 уровней), название подразделения и город по `IDDEP`.

**Часть 4: Отбор сотрудников и профессиональная вредность → итоговая KASPI_EMP**

В итоговую таблицу собираются две группы сотрудников:
- **Группа A — по названию должности и подразделению** (`KASPI_EMP_FILTERED`):
  - отбираются должности из списка и по маске (раздел 6);
  - для каждого сотрудника строится `POSITION_KEY` — ключ для поиска профессиональной вредности;
  - признак `IsNeededEmployee = 1`;
  - вредность подтягивается из INLINE-справочника по `POSITION_KEY`.
- **Группа B — по ID должности из Excel** (`KASPI_EMP_NESTED`):
  - берутся сотрудники, чей ID должности есть в `Новые позиции для отчёта.xlsx` (`INNER JOIN`, остальные отбрасываются);
  - вредность берётся из этого же файла (колонка «Проф.вредность»).
- Группы объединяются через `CONCATENATE`. У группы B признаков `IsNeededEmployee` и `POSITION_KEY` нет (пусто).

**Часть 5: LAST_MED — медосмотры**
- **Источник:** `Дата последнего медосмотра.xlsx` (лист «Лист1»).
- **Поля:** `STATUS_TABNO` (табельный номер) и `Дата последнего медосмотра`. Связь с `KASPI_EMP` — по `STATUS_TABNO`.

### Тип события в кадровых данных (расчёт стажа)

| Событие | Условие |
|---------|---------|
| **Приём** | Первая запись компании (`CORPID`) или перерыв между периодами больше 14 дней |
| **Перевод** | Изменился тип контракта или пара «подразделение + должность», а перерыв не больше 14 дней |
| **Увольнение** | У периода есть дата окончания, и следующая запись начинается позже чем через 14 дней (или её нет) |

Операции с признаком «Увольнение», а также записи, предшествующие операции «Прием на работу» в рамках того же табельного номера и компании, не считаются действующими. Из нескольких записей одного дня берётся одна.

### Сшивка периодов (UNI и CORP)
Периоды одного сотрудника могут пересекаться (несколько ставок, перевод между компаниями). Они сшиваются по приоритету: при пересечении остаётся запись с большей ставкой (`STATUS_RATE ≥ 0,5` или больше ставки в соседней записи), у проигравшей дата начала становится пустой, и запись отбрасывается. Сдвиг начала на день после конца соседнего периода предусмотрен только для пересечения периода «ГПХ» со «Штатом», а в этой версии скрипта ГПХ не загружается. Сшивка делается два раза:
- по сотруднику (`UNIID` = ИИН), логика «Kaspi.kz»; идентификатор компании заменяется на `ИИН-Kaspi.kz`;
- по каждой компании (`CORPID` = ИИН-БИН), логика «Каждое АО/ТОО отдельно».

### Стаж
- **Дата приёма** — ближайшая слева дата события «приём» (`FirstSortedValue` от максимальной даты приёма, не позже начала периода). При повторном приёме стаж начинается заново.
- **Конец периода для стажа** — вчера, если периода окончания нет или он в будущем; иначе дата окончания.
- **Стаж:** разница в днях с учётом первого дня, делённая на 30,4 и округлённая вниз с шагом 0,1.
- **Период для расчёта** — последний по дате начала у каждого `STATUS_IDEMPL`.

### Должность по ФИО
Из `S0008.EMPLOYEES` отбираются записи без даты увольнения (или с увольнением раньше приёма — повторный приём). Из них для каждого ФИО берётся запись с самой поздней датой приёма.

## 7. Примечания

**Отбор и вредность**
- **Сотрудник может попасть в итог дважды.** Если и название его должности подходит под правила группы A, и ID должности есть в Excel (группа B), строки двух групп просто склеиваются, а не дедуплицируются. Вредность в них может различаться. Нужно проверить на данных.
- **Не у всех должностей группы A есть вредность.** В INLINE-справочнике нет строк для «Специалист по Подготовке Инкассаторов» и «Дежурный Инкассатор по Вооружению», а для инженеров перечислены только некоторые города. Для остальных вредность останется пустой (если должность не покрыта группой B).
- **Ключ `POSITION_KEY` строится из полного названия должности.** Для руководителей групп и начальников отделов отбор идёт по маске («Руководитель группы…», «Начальник отдела…»), а ключ в INLINE записан коротко («Руководитель Группы|Дирекция Инфраструктуры»). Поиск вредности сработает только если название должности в HR состоит именно из этих слов без уточнений. Регистр в ключах должен совпадать с HR.
- **Названия должностей обрезаны.** В списках встречаются «Специалист по Обслуживанию Зда», «Ведущий Специалист по Обслужив», «Инженер 2 Категории в г.Карага» — похоже, поле `POSITION` в источнике обрезается до 30 символов. Если формат изменится, точное совпадение перестанет работать.
- **Точное совпадение чувствительно к регистру.** Список должностей проверяется функцией `Match`, а не `MixMatch`. Изменение регистра в HR (например, «Водитель» → «водитель») выведет сотрудника из отбора.
- **`IsNeededEmployee` заполнен только для группы A.** Если использовать его как фильтр в интерфейсе, сотрудники группы B пропадут.
- **Правила отбора зашиты в скрипт.** Новые должности по названию добавляются правкой кода, а по ID — через Excel `Новые позиции для отчёта.xlsx`.

**Что считается, но не используется**
- Бо́льшая часть скрипта (разбор приёмов, переводов, увольнений, 20+ признаков «Внутри уровня …», «Откуда: …», `PREV_*`, `EVERYDAY_RATE`, `IntervalMatch`) считается и удаляется (`DROP TABLE STATUS`, `PREV_DEPARTMENTS` и др.). Из всего этого в модели остаются только стаж и дата приёма из `STATUS_FINAL`. Это увеличивает время загрузки.
- В этой версии скрипта все записи загружаются как «Штат». Условия для «ГПХ» не срабатывают.
- Закомментированный блок с датой рождения, полом, телефоном и e-mail (`EMPLLIST`) не используется: пол и дата рождения берутся из `STATUS.qvd`.
- Исходная (неотобранная) таблица сотрудников удаляется (`DROP TABLE KASPI_EMP`), в модели остаются только отобранные.

**Связи в модели**
- **`MasterCalendar` ни с чем не связан.** В итоговых таблицах нет поля `Дата`, календарь работает только через формулы в интерфейсе.
- **Возможны дубли в `STATUS_FINAL`.** В расчёт попадают записи обеих логик («Kaspi.kz» и «Каждое АО/ТОО отдельно»). У одного `STATUS_IDEMPL` может остаться две строки с одинаковым максимальным началом периода. Если значения стажа в них разные, у сотрудника будет несколько значений стажа. Нужно проверить на данных.
- **Связь с медосмотрами идёт по табельному номеру** (`STATUS_TABNO`). Если в Excel номер записан с другим форматом (текст, ведущие нули), связь не сработает. Дубли табельных номеров в Excel создадут несколько дат на сотрудника.
- **Поле `KEY_FIO` удаляется из модели.** Команда `Drop Field KEY_FIO` убирает его и из справочника сотрудников. Для дальнейших связей по ФИО ключ придётся строить заново.
- **Должность подтягивается по ФИО.** У полных тёзок должность и табельный номер могут оказаться чужими, и тогда сотрудник попадёт в отбор или вредность по чужой должности.
- **`STATUS_HIRE_DATE` в `STATUS_FINAL`** — это расчётная дата приёма, а `Дата приёма` в `KASPI_EMP` — значение из `STATUS.qvd`. Они могут отличаться, и это два разных поля.

**Хрупкие места**
- Пороги зашиты в код: перерыв 14 дней между приёмом, переводом и увольнением, ставка 0,5 для приоритета, 30,4 дня в месяце для стажа.
- Дата среза «сегодня − 2 дня» зашита константой.
- Если вчерашний день не конец месяца, он всё равно получает флаг «Конец месяца» — так задумано, чтобы текущий месяц показывался по последнюю дату.
- Стаж — приблизительный (месяц равен 30,4 дня), не календарный.

**Персональные данные**
- В закомментированном тест-блоке в тексте запроса `S0008$STAFOPERDATA` хранятся реальные ИИН сотрудников и идентификатор записи. Эти строки лучше удалить перед передачей скрипта другим.
- Таблица `KASPI_EMP` содержит ИИН, ФИО, дату рождения и данные о медосмотрах. Доступ к приложению стоит ограничить.

**Ручные источники:** `Новые позиции для отчёта.xlsx` и `Дата последнего медосмотра.xlsx` обновляются вручную. Если файла медосмотров нет, загрузка скрипта остановится на `LAST_MED`.

**Обновление:** полная перезагрузка при каждом reload. Календарь, стаж и срез сотрудников пересчитываются относительно даты загрузки.
