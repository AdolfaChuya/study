h2. 3. Схема связей

Явных JOIN-ов в SQL нет (используются оконные функции над одной таблицей). На уровне Qlik-скрипта — 2 join, но их порядок и направление важны для понимания итогового результата:

{code}
Лист1 (CODE, KHE)                                   ["Exel"]
    └─ INNER JOIN Лист2 (KHE, Подразделение по КХЕ)  ON KHE
           └─ RIGHT JOIN Resident ReportOSNMA        ON CODE
{code}

Смысл цепочки: сначала строится справочник «инвентарный номер → КХЕ → подразделение» (через {{INNER JOIN}} по {{KHE}} — попадут только КХЕ, присутствующие в обоих листах Excel), а затем этот справочник {{RIGHT JOIN}}-ится к резидентной копии факта {{ReportOSNMA}} по {{CODE}} — правый join гарантирует, что *все строки факта сохраняются*, даже если инвентарный номер не нашёлся в Excel-справочнике (поля {{KHE}} / «Подразделение по КХЕ» в этом случае будут пустыми).

h2. 4. Структура данных

Отчёт состоит из одной логической части (без {{UNION ALL}}) — факт из StarRocks, дообогащённый двумя Excel-справочниками.

*Часть 1: ReportOSNMA — реестр ОС/НМА с амортизацией*
* *Источник:* {{BI_VIEW.S0008_REPORTOSNMA}}
* *Связи:* в самом SQL связей с другими таблицами нет; вместо джойна используются оконные функции {{LAST_VALUE(...) OVER (PARTITION BY CODE)}} — для каждого инвентарного номера ({{CODE}}) подтягивается «последнее» значение подразделения/МОЛ/адреса среди всех строк с этим кодом
* *Фильтры:* {{YEAR(DATE_BEGIN) = 2026}} (жёстко зафиксированный год — см. примечания); {{KODKOF IN (...)}} — ограниченный список из 76 кодов классификатора ОС (КОФ)
* *Признак:* {{QUANTITY = COUNT(CODE) OVER (PARTITION BY CODE)}} — количество строк с одинаковым инвентарным номером (индикатор задвоения объекта в источнике)

*Часть 2 (обогащение в Qlik): подразделение по инвентарному номеру*
* *Источник:* {{Амортизация_.xlsx}} (Лист1 + Лист2)
* *Связи:* {{INNER JOIN}} по {{KHE}}, затем {{RIGHT JOIN}} результата к {{Resident ReportOSNMA}} по {{CODE}}
* *Фильтры:* —
* *Признак:* после джойна резидентная копия {{ReportOSNMA}} удаляется ({{DROP TABLE}}) — данные остаются только в объединённой таблице

h2. 6. Бизнес-логика

*Определение города по коду/наименованию подразделения:*

||Условие||Результат||
|{{CIT}} содержит «111»|«Головной Банк (ЗИП)»|
|{{CIT}} содержит «Южная»|«Алматы»|
|Иначе|Текст после «г. » в наименовании подразделения ({{SubField(CIT,'г. ',2)}})|

*Ограничение по классификатору ОС/НМА:* отчёт включает только объекты с кодом {{KODKOF}} из фиксированного списка (76 значений) — то есть не все категории основных средств и НМА попадают в отчёт, а только те, что относятся к отслеживаемым в этом дашборде классам.

*Правило обогащения подразделением:* соответствие «инвентарный номер → КХЕ» и «КХЕ → подразделение» ищется во внешнем Excel-файле; если инвентарный номер не найден — строка факта всё равно остаётся ({{RIGHT JOIN}}), но поля КХЕ/подразделения из Excel будут пустыми.

h2. 7. Примечания

* Фильтр {{YEAR(A.DATE_BEGIN) = 2026}} жёстко зафиксирован в SQL — при переходе на новый отчётный год потребуется вручную обновить значение в скрипте (не параметризовано).
* *Потенциальное ограничение:* {{LAST_VALUE(...) OVER (PARTITION BY CODE)}} использован *без {{ORDER BY}}* внутри оконной функции. Без сортировки результат «последнего» значения в партиции формально зависит от порядка, в котором СУБД физически возвращает строки, и может быть неустойчивым между запусками. Если требуется гарантированно "последнее по дате" значение (например, актуальное подразделение/МОЛ), в {{OVER}} стоит добавить {{ORDER BY DATE_BEGIN DESC}} (или аналогичное поле) — рекомендуется уточнить у автора отчёта, было ли отсутствие сортировки осознанным решением.
* Итоговое имя объединённой таблицы после цепочки {{Exel → INNER JOIN SPR → RIGHT JOIN Resident ReportOSNMA}} в самом скрипте не задаётся явным финальным {{Load ... As ИмяТаблицы}} — при сопровождении стоит открыть модель данных в приложении и проверить, под каким именем ({{Exel}} или {{SPR}}) таблица видна для дальнейших ссылок/измерений.
* Справочник {{Амортизация_.xlsx}} — внешний файл на файловом ресурсе {{lib://kaspi_service (hq_samenov_55251)}}, обновляется вручную вне Qlik-скрипта; при рассинхронизации КХЕ/подразделение по новым инвентарным номерам подтягиваться не будут.
* Связанные отчёты: не выявлены по содержимому скрипта.
