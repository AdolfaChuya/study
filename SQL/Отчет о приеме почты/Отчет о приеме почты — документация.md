# Отчет о приеме почты

Отчёт о приёме почтовых отправлений Центральным архивом (ЦА): конверты с документами и коробки (посылки) из филиалов. Данные с 01.01.2025.

Отчёт показывает:
- сколько конвертов принято по дням, подразделениям, городам и типам архива;
- сколько в них клиентских досье (физ. и юр. лица), рекламаций, кассовых и дополнительных документов;
- что находится в пути (создано по датам создания);
- сколько коробок принято, их контрольный и первичный вес;
- построчную детализацию по конвертам и сшивам;
- сырые события по коробкам.

## 3. Схема связей

```
Таблица 1: Сводная по дням  ← Z_KAS_ENVELOPE (env, C_POINT = 15150062740, дата приёма ≥ 2025-01-01)
    ├─ LEFT JOIN Z_STRUCT_DEPART (d)          ON ID = C_ST_DEPART
    │    ├─ LEFT JOIN Z_KAS_UNIVERSAL_D (zkud) ON C_KAS_DEPART_GROUP = ID   → группа подразделения
    │    └─ LEFT JOIN address_dict (Z_ADRESSES) ON C_ADDRESSES = COLLECTION_ID → город
    ├─ LEFT JOIN Z_KAS_UNIVERSAL_D (arch)      ON ID = C_ARCH_TYPE         → тип архива
    ├─ LEFT JOIN cash_by_collection            ON C_CASH_DOCS_ARR (тип 461342831869)
    ├─ LEFT JOIN dop_docs                      ON C_CASH_DOCS_ARR (тип 501008167835)
    ├─ LEFT JOIN dossier_all (Z_FOLDERS)       ON C_KAS_ENVELOPE = env.id
    └─ LEFT JOIN recl_counts (Z_KAS_RECL_HIST) ON C_KAS_ENVELOPE = env.id

Таблица 3: Коробки  ← KZ_ARCHIVE_BOX_EVENT_PROD (дедупликация по штрихкоду)
    └─ LEFT JOIN final_depart  ON senderName = ФИО сотрудника
          ├─ s01_result (приоритет 1): Z_USER → Z_STRUCT_DEPART → Z_ADRESSES
          └─ motiv_result (приоритет 2): S0108.DOCUMENTS → EMPLOYER, DEPARTMENT

Итоговая модель Qlik:
Calendar (Date) ── RFO_Archive_Summary ([Дата поступления]) ── RFO_Archive_Boxes ([Дата поступления])
            ├──── RFO_Archive_InTransit ([Дата создания (в пути)])
            └──── ABC_Test_Data ([Принят в ЦА])
BOX_DATA — отдельная таблица (связей нет)
```

## 4. Структура данных

**Часть 1: RFO_Archive_Summary — сводная по дням**
- **Источник:** `S01.Z_KAS_ENVELOPE` и связанные таблицы S01.
- **Гранулярность:** день приёма × подразделение × группа × город × тип архива.
- **Фильтры:** `C_POINT = '15150062740'`, `C_DATE_PROCESSING >= 2025-01-01`.
- **Период:** метка недели (раздел 6).
- **Метрики:**
  - принято конвертов (кроме кассовых и доп. документов);
  - физ. и юр. клиенты (количество досье и рекламаций);
  - кассовые конверты и документы, безналичные переводы;
  - конверты и документы типа «Доп. документы».

**Часть 2: RFO_Archive_InTransit — документы «в пути»**
- **Источник:** `S01.Z_KAS_ENVELOPE`, дата создания ≥ 2025-01-01. Фильтра по точке (`C_POINT`) и по статусу нет.
- **Гранулярность:** дата создания конверта.
- **Метрики:** досье + рекламации, кассовые документы, доп. документы по создавшимся конвертам. Сколько из них уже принято, определяется в интерфейсе сопоставлением с таблицей 1.

**Часть 3: RFO_Archive_Boxes — коробки**
- **Источник:** `S0266.KZ_ARCHIVE_BOX_EVENT_PROD` (JSON), статус коробки «Принято в ЦА», заполненная дата приёма.
- **Дедупликация:** одна запись на штрихкод — с самой поздней датой отправки, при равенстве — с максимальным id события.
- **Подразделение отправителя:** по ФИО отправителя находится подразделение в S01 (приоритет), а если там нет — в S0108.
- **Город:** адрес подразделения из `Z_ADRESSES`; если адреса нет — из названия подразделения (первая часть до запятой без префиксов «Филиал », «Отделение »).
- **Гранулярность:** дата приёма × город × подразделение отправителя.
- **Дополнительные строки:** из Excel `Посылки КГПО_Алматы.xlsx` дописываются посылки КГПО (у них первичный вес = 0).
- **Признак:** `Тип посылки` = «ЕМС» для данных из системы; для Excel — значение из файла.

**Часть 4: ABC_Test_Data — детализация по конвертам**
- **Источник:** `S01.Z_KAS_ENVELOPE` (`C_POINT = '15150062740'`, без фильтра по дате) + строки `Z_KAS_UNIVERSAL_S` по коллекции документов конверта.
- **Гранулярность:** конверт × строка документа (сшив). Показатели уровня конверта (досье, рекламации, доп. документы) повторяются на каждой строке.
- **Содержание:** номер и даты конверта, ФИО менеджера, подразделение, код, группа, город, тип архива, код и наименование сшива, количество документов в сшиве, признак `is_sheet`.

**Часть 5: BOX_DATA — сырые события по коробкам**
- **Источник:** `S0266.KZ_ARCHIVE_BOX_EVENT_PROD`, статус «Принято в ЦА».
- Все события без дедупликации, все поля JSON развёрнуты в колонки (адреса, получатель, вес, логин, штрихкод).

**Часть 6: Calendar**
- Диапазон дат: общий минимум и максимум по таблицам 1, 2 и 4.
- Связь по полю `Date`, которое добавляется в таблицы 1, 2 и 4 через `LEFT JOIN`.
- Поля: год, месяц, год-месяц, квартал и его номер, день, неделя, день недели.

## 6. Бизнес-логика

### Типы архива (по идентификаторам)

| Идентификатор типа | Как используется |
|--------------------|------------------|
| 461342831869 | Кассовые документы: попадают в «Касса Конверт» и считаются по `Z_KAS_UNIVERSAL_S` |
| 501008167835 | Дополнительные документы: попадают в «Доп документы», количество — `SUM(C_I1)` |
| 24836598006 | Рекламации: количество берётся из `Z_KAS_RECL_HIST` |
| 14717996203, 14717996311, 157640900720, 256100987278, 342666015468 | Досье: количество берётся из `Z_FOLDERS`. Тип 342666015468 дополнительно считается как юр. клиенты |

Названия типов в скрипте не заданы — они приходят из справочника `Z_KAS_UNIVERSAL_D`.

### Недельный период
Недели считаются с понедельника, но не пересекают границу месяца в начале периода: `Начало = max(понедельник недели, 1-е число месяца)`, `Конец = Начало + 6 дней`. Период выводится как `дд.мм-дд.мм`.

### Количество документов в сшиве
Для строки кассового документа: если у неё есть подкрепления (дочерние строки по `C_R1`), берётся их число; иначе значение `C_N1`.

### Определение подразделения отправителя коробки
1. **S01 (приоритет 1).** Пользователь `Z_USER` с совпадающим ФИО, допускается суффикс в скобках (например, `Иванов И.И. (филиал)`). Берётся последняя версия по `S$CHANGE_DATE`, подразделение и адрес из `Z_STRUCT_DEPART`.
2. **S0108 (приоритет 2, только если в S01 нет).** Подразделение автора документа, созданного ближе всего по времени к отправке коробки (не позже даты отправки, не удалён).
3. Город: из адреса подразделения, иначе из названия подразделения (без префиксов «Филиал », «Отделение »).

## 7. Примечания

**Проверить по данным**
- **Недельный период может перекрываться.** Конец периода — всегда начало плюс 6 дней и не обрезается по концу месяца. Если месяц начинается в середине недели (например, 1 октября — среда), метка первой недели получается `01.10-07.10`, хотя следующая неделя начинается 6 октября и имеет метку `06.10-12.10`. Диапазоны в метках пересекаются: даты 6 и 7 октября входят в оба диапазона, хотя фактически относятся ко второй метке. Для недель, переходящих через границу месяца, метка конца выходит в следующий месяц. Нужно уточнить у заказчика, нужна ли обрезка по концу месяца.
- **Возможный двойной счёт кассовых документов.** В запрос по кассовым строкам попадают все строки коллекции с заполненным `C_N1`, в том числе подкрепления (у них `C_R1` не пуст), если у них тоже заполнен `C_N1`. Для родительского сшива берётся число подкреплений, а затем подкрепления складываются ещё раз по своим `C_N1`. В детализации для этого есть признак `is_sheet`, но в сводных таблицах он не используется. Проверить на реальных данных.
- **`Кассовые документы` + `Безналичные переводы` может не совпадать с `Касса КД+БП`.** Строки с пустым `C_S2` попадают только в общую сумму: условия `!=` и `=` для пустого значения не срабатывают.
- **Нет дедупликации по `ID` конверта.** `Z_KAS_ENVELOPE` читается из поля `AFTER_BODY`. Если в таблице хранятся несколько версий записи конверта, он посчитается несколько раз. Для адресов и сотрудников дедупликация есть, для конвертов нет.
- **Таблица «в пути» не фильтрует по статусу.** В неё попадают все конверты, созданные с 01.01.2025, а не только не принятые. «В пути» получается сопоставлением с принятыми в интерфейсе.

**Потери и несоответствия данных**
- **История состояний не загружается.** В SQL запроса детализации строится `status_history_text` (история точек конверта), в Qlik она есть во внутреннем `LOAD` как `[История состояний]`, но во внешнем `LOAD` её нет. Поле не доходит до модели, хотя запрос на её построение (`GROUP_CONCAT`) выполняется.
- **Таблица детализации называется `ABC_Test_Data`.** Название тестовое, но она используется в календаре и, вероятно, в отчётах.
- **Разные фильтры по датам.** Сводная — с 01.01.2025 по дате приёма, в пути — с 01.01.2025 по дате создания, детализация — без ограничения. Календарь растягивается до самой ранней даты в детализации.
- **Коробки не получают поле `Date`.** Таблица связана с календарём косвенно через общее поле `Дата поступления` со сводной.
- **Города и подразделения коробок и конвертов называются по-разному** (`Свод Город Коробки` против `Свод Город`) и не связаны между собой.
- **Регистр полей `BOX_DATA`.** В таблице есть и `RECEIVEDATE` (из колонки), и `receiveDate` (из JSON). Qlik считает их разными полями.

**Жёстко заданные значения**
- Точка конверта `15150062740` и идентификаторы типов архива зашиты в запросы в нескольких местах.
- Параметры запросов: `query_timeout = 3600`, `exec_mem_limit = 20 ГБ` — запросы тяжёлые.

**Ручные источники:** `Посылки КГПО_Алматы.xlsx` нужно обновлять вручную. Формат веса — с запятой как десятичным разделителем.

**Обновление:** полная перезагрузка при каждом reload, без инкрементальной загрузки.
