# Отмененные заявки

Анализ возвратов и отмен заявок на оплату (KAS / IBSO) по бюджетам КХЕ Kaspi Сервис 1300, 1310, 1320, 1140, 1340, 1350, 1360, 1370. Данные с 01.01.2024.

Отчёт показывает по каждой неоплаченной заявке:
- кто и на каком этапе её вернул (из какого статуса, в какой);
- причину возврата: сырой текст и категория, определённая по ключевым словам;
- через сколько времени после создания заявку вернули;
- кто инициатор и кто вернул, их должности и статусы работы.

Рядом лежат оплаченные заявки и план бюджета, чтобы сопоставлять отмены с фактом и планом.

## 3. Схема связей

```
bi.f$kas_request_pay (t)   [Оплачено → BUDGET_PAID | не Оплачено → BUDGET]
    ├─ LEFT JOIN bi.f$kas_request_pay2850 (a)  ON r_id И code_expense
    ├─ LEFT JOIN s06.z#hozed (h4, КХЕ филиала ДБУ)  ON a.c_kxe = h4.id
    └─ LEFT JOIN s06.z#hozed (h5, КХЕ бюджета ДБУ)  ON a.c_kxe_remap = h5.id
UNION ALL  план бюджета: s06.z#tmc_rash_stats × z#spr_code_expense × z#hozed × z#kas_spr_rashod
                          (UNPIVOT по месяцам)
    └─ LEFT JOIN s06.z#hozed (h6) — название КХЕ для свода

Обогащение таблицы BUDGET (неоплаченные заявки):
BUDGET
    ├─ LEFT JOIN Tmp_Заявки  ON Номер заявки (+ ФИО, причины, дата возврата, кто вернул, статусы)
    │      ├─ LEFT JOIN S0008.USERS    ON Email (+ Отчество)   → табельный по email
    │      └─ LEFT JOIN S0008.USERS    ON ФИО_КЛЮЧ             → табельный по ФИО
    ├─ LEFT JOIN Tmp_StaffList  ON Табельный инициатора        → должность и статус инициатора
    ├─ LEFT JOIN Tmp_StaffList  ON Кто вернул (= EMPL_NAME)    → должность и статус вернувшего
    ├─ ApplyMap Map_StageByName ON Кто вернул                  → этап (запасной вариант)
    └─ ApplyMap Map_GeneralReason / Map_Stage                  → Общая причина, Этап

Итоговая модель Qlik:
CALENDAR (DT_Ключ) ──── BUDGET_FINAL (оплаченные и неоплаченные) ──── Справочник КХЕ (КХЕ инициатора)
BI.SELF_SERVICE_DEVICES_CNT_V — отдельная таблица (поля REP_DATE, CNT_SERIAL_NUMBER, KHE)
```

## 4. Структура данных

**Часть 1: BUDGET_PAID — оплаченные заявки**
- **Источник:** `bi.f$kas_request_pay` + `f$kas_request_pay2850` + `z#hozed`.
- **Фильтры:** `r_kxe_budget` из списка 1300, 1310, 1320, 1140, 1340, 1350, 1360, 1370; `state = 'Оплачено'`; `date_req > 01.01.2024`.
- **Признак:** `Статус заявки = 'Оплачено'`. Поля возврата и этапы пустые.
- К заявке добавляются инициатор и его email из `z#kas_request_pay` (только `STATE_ID = 'PAID'`).

**Часть 2: BUDGET — неоплаченные заявки (основной объект отчёта)**
- **Источник и фильтры** те же, но `state != 'Оплачено'`.
- Строки обогащаются данными о возврате, сотрудниками и должностями (подробно в разделе 6).

**Часть 3: План бюджета (UNION ALL внутри обоих запросов)**
- **Источник:** `z#tmc_rash_stats` × `z#spr_code_expense` × `z#hozed` × `z#kas_spr_rashod`.
- **Фильтры:** год ≥ 2022, КХЕ из расширенного списка (501, 502, 503, 902, 1160, 1800, 1300, 1310, 1320, 1140, 1340, 1350, 1360, 1370, 1250, 1270, 1240, 1245, 1120, 1330), сумма ≠ 0.
- **Признак:** `Тип документы = 'Документы плана'`, поле `План` заполнено.
- Месячные колонки разворачиваются через UNPIVOT в строки с датой на 1-е число месяца.

**Часть 4: BUDGET_FINAL**
- Результат вычислений над BUDGET: `Базовая Категория`, `Категория причин`, `Общая причина`, `Этап рассмотрения`, `Этап`.
- Таблицы BUDGET_PAID и BUDGET_FINAL содержат одинаковый набор полей, и Qlik автоматически склеивает их в одну таблицу. Оплаченные заявки получают пустые поля возврата.

**Часть 5: Календарь** — `CALENDAR` с 01.01.2022 по 31.12.2026: год, месяц, квартал, флаги «Текущий год» и «Текущий месяц». Связь по `DT_Ключ`.

**Часть 6: Справочник КХЕ** — INLINE-таблица кодов и названий (101–143 — города, 501–1800 — подразделения Kaspi Сервис). Связь по `КХЕ инициатора`.

**Часть 7: `SELF_SERVICE_DEVICES_CNT_V`** — количество устройств самообслуживания по КХЕ. Поле `KHE` не называется `КХЕ инициатора`, поэтому таблица остаётся отдельной.

## 6. Бизнес-логика

### Разбор последнего возврата заявки
Из текста `C_ARHIV_RET_REASON` (переносы строк убираются) берётся **последняя** дата в формате `ДД.ММ.ГГГГ чч:мм:сс`. От неё отсчитывается остальное:

| Поле | Как вычисляется |
|------|-----------------|
| `Дата/время возврата` | Последняя найденная дата |
| `Из статуса` | Значение `Из статуса:"…"` в блоке перед датой. Если такой метки нет, берётся текст статуса перед датой |
| `Кто вернул` | Текст после даты до `В статус:` (или до `Причина:`) |
| `В статус` | Значение `В статус:"…"` после даты. Если `Из статуса` равен «Не обработано» или «На возврат инициатору», то `В статус = 'Отменено'` |

### Время отклонения
`Время отклонения = Дата/время возврата − Дата заявки`. Если разность отрицательная, к ней добавляется 0,5 суток (12 часов). Результат выводится как интервал `чч:чч:сс`.

### Табельный номер инициатора
1. По email (самая свежая запись по `LAST_LOGIN`, ключ — email + отчество).
2. Если не нашёлся — по склеенному ФИО (`Фамилия Имя Отчество` в верхнем регистре).

### Этап рассмотрения
Правила применяются по порядку, срабатывает первое:

| Условие | Этап |
|---------|------|
| Нет записи возврата в архиве | Инициатор |
| Инициатор = вернувший, или `Из статуса = 'На возврат инициатору'`, или `Из статуса = 'Не обработано'` | Инициатор |
| `Из статуса = 'В работе'` | Контролер |
| `Из статуса` — «В работе ДБУ» или «Передано в ДБУ» | ДБУ |
| `Из статуса = 'В работе УКЗИ'` | УКЗИ |
| Должность вернувшего «Исполнительный Директор» | Согласующий 1-го уровня |
| Должность вернувшего «Управляющий Директор» | Согласующий 2-го уровня |
| Должность вернувшего содержит «Заместитель Председателя Правления» | Согласующий 3-го уровня |
| Остальное | Значение из `Справочник по этапам расс.xlsx` по ФИО вернувшего. Если и там нет — «Инициатор» при `Из статуса = В статус = 'Отменено'`, иначе пусто |

Затем `Этап` — номер по справочнику: Инициатор 1, Контролер 2, УКЗИ 3, Доп. Согласующий 4, Согласующие 1-го / 2-го / 3-го уровня 5 / 6 / 7, ДБУ 8. Неизвестные значения → «Неизвестный этап».

### Классификация причин возврата
Категория определяется по тексту `Причина возврата`.

1. **Базовая Категория** — цепочка из 100+ правил по ключевым словам, первое сработавшее побеждает. Основные группы:
   - пустое значение или символы `- . / ошибка` → «Неизвестно»;
   - ключевые слова: дубль, ЭСФ, КХЕ, НДС, договор, СНР, детализация, 1С, бюджет, сумма, назначение, поставщик, документы, счёт, тест;
   - иначе → «Прочие».
2. **Категория причин** — если базовая категория «Прочие», подключаются четыре дополнительных блока правил (примерно 160 условий), в том числе по типичным формулировкам в тексте. Первый блок, вернувший значение, побеждает. Если ничего не подошло — «Прочие».
3. **Общая причина** — укрупнение категории по справочнику, например:
   - Некорректный НДС → «Некорректная сумма»;
   - Некорректная детализация, Некорректное назначение, Некорректный вид платежа, Некорректный поставщик, Некорректный выбор «В бюджете» → «Некорректное заведение заявки»;
   - Неактуальный счёт, Некорректная дата в ЭСФ → «Некорректные документы»;
   - значения без записи в справочнике → «Другие».

### Прочее
- **Замена казахских символов:** `MapSubstring` меняет искажённые символы (Ќ, ў, Ґ, ї и др.) на казахские буквы (Қ, ұ, Ө, ү и др.) в ФИО инициатора и вернувшего.
- **Вид затрат:** по коду затрат, правило в таблице выше.
- **Сумма НДС:** 12/112 от суммы с НДС, только если у заявки признак НДС = 1.

## 7. Примечания

**Ошибки в правилах**
- **Правило `'*?*'` перекрывает остальные.** В блоке 4 правил категории причин условие `WildMatch([Причина возврата], '*?*')` стоит раньше многих других. В `WildMatch` символ `?` означает «любой один символ», а не буквальный знак вопроса. Поэтому любой непустой текст, не попавший в блоки 1–3 и в более ранние правила блока 4, уходит в «Вопросы к стоимости/выбору позиций». Все правила блока 4 после этой строки не срабатывают, и «Прочие» остаётся только для пустых значений. Если нужен именно вопросительный знак, нужно писать `'*\?*'` или перенести проверку в конец.
- **Дубли в `Базовая Категория`.** Условие «пустая причина → Неизвестно» повторяется трижды (с `Match` и `MixMatch`), условие `'?'` — дважды. Это не мешает расчёту, но затрудняет сопровождение.

**Целостность данных**
- **Размножение строк при поиске должности.** Должность вернувшего подтягивается по ФИО (`EMPL_NAME`), а `Tmp_StaffList` содержит по строке на каждый табельный номер. Если у человека несколько табельных (повторный приём, перевод) или есть полные тёзки, строки заявки задваиваются, а суммы `Факт` и `Сумма заявки` завышаются.
- **Берётся только последний возврат.** Если заявку возвращали несколько раз, в полях «Дата/время возврата», «Кто вернул», «Из статуса», «В статус» остаётся последний возврат. Остальные видны только в сыром тексте `Причины возврата список`.
- **Разбор текста возврата.** Он опирается на формат записи (даты, метки `Из статуса:`, `В статус:`, `Причина:`). Если формат изменится, поля возврата станут пустыми, а этап — «Инициатор».
- **Склейка оплаченных и неоплаченных заявок зависит от одинакового набора полей.** Если добавить поле только в одну из двух частей, Qlik создаст две отдельные таблицы с синтетическими ключами.
- **Строки плана в оплаченной части.** В запрос по оплаченным заявкам тоже попадает план (UNION ALL), но `План` в нём перезаписывается пустой строкой. Таких строк нет в сумме плана, но они увеличивают количество записей.

**Хрупкие места**
- **Календарь ограничен 31.12.2026.** Конец календаря задан константой. После нового года даты заявок останутся без календаря. Нужно обновить границу (например, сделать её зависимой от `Today()`).
- **Бюджет по КХЕ задан жёстко списком:** 1300, 1310, 1320, 1140, 1340, 1350, 1360, 1370 для заявок и более широкий список для плана. Новые КХЕ нужно добавлять в двух запросах (оплаченные и неоплаченные), а также в запросе плана.
- **`BI.SELF_SERVICE_DEVICES_CNT_V` загружается без `LOAD` и не связана с моделью.** Нужна ли она в отчёте — стоит уточнить.
- **Остались неиспользуемые вычисления.** Поля `hozedid4svod`, `code_expense4svod`, `chk1`, `ls2`, `MD5` считаются в SQL, но не попадают в `LOAD`.
- **`LIB CONNECT TO 'staroks (BKS)'` стоит в середине скрипта.** Всё после него, включая `Tmp_StaffList`, выполняется в Starrocks, хотя комментарий в скрипте называет его «Oracle».
- **Ручные файлы:** `Справочник по этапам расс.xlsx` (соответствие ФИО → этап) нужно обновлять вручную, иначе новые согласующие не получат этап.

**Связанные материалы:** рядом на рабочем столе лежит `Отмененные заявки проверка.docx` (не открывал).

**Обновление:** полная перезагрузка при каждом reload, инкрементальной загрузки нет.
