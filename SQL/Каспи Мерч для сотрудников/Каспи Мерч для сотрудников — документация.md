# Каспи Мерч для сотрудников

Аналитика продаж брендированного мерча Kaspi. Магазин Ucon store (Uconstore) на Kaspi Магазине.

Отчёт охватывает:
- заказы с 01.10.2024;
- профиль покупателя: пол, возраст, должность и категория должности, подразделение;
- география доставки;
- отмены, возвраты и отзывы;
- ценовые категории товаров;
- воронка кликов на витрине.

| Поле | Описание |

## 3. Схема связей

Как собирается таблица заказов:

```
s43$ord_v (t)  [merch_id = 92448]
    ├─ JOIN s43$orderentries_v (e)       ON t.order_pk = e.p_order
    └─ JOIN s43$prod_master_v (s)        ON s.sku = e.sku  [brand_id = 103280]
         → ORDERS (Qlik)
            ├─ ApplyMap STATUS_MAP          ON ИИН          → ФИО
            ├─ ApplyMap GENDER_MAP          ON ФИО          → пол (запасной вариант)
            ├─ ApplyMap City_Region_Mapping ON CITYTO       → регион
            ├─ LEFT JOIN ENUMERATIONVALUESLP        ON CANCELREASON_CODE
            ├─ LEFT JOIN S0043_SHOP_CUSTOMER_REVIEW ON ORDERCODE + PRODUCT_SKU
            ├─ LEFT JOIN EMPLOYEES+USERS_POSITIONS  ON BUYER_FIO  → POSITION, ID
            │    └─ LEFT JOIN Position ID CATEGORY  ON ID         → category
            ├─ LEFT JOIN S0043_ORDERS               ON ORDERCODE  → current_status_status
            ├─ LEFT JOIN Возвраты отработка.xlsx    ON ORDERCODE + PRODUCT_SKU
            └─ LEFT JOIN stock_merch_v              ON PRODUCT_SKU → CATEGORY, PARENT_CATEGORY
         → ORDERS_FINAL
```

Итоговая модель Qlik:

```
ORDERS_FINAL
    ├─ ORDERDATE          → ORDERDATE_CALENDAR
    ├─ BUYER_IIN          → DEP_TABLE → DEPART_ID → Hierarchy (подразделения)
    ├─ PRODUCT_SKU        → Каспи магазин.xlsx (справочник товаров)
    ├─ VIEW_KEY           → PRODUCT_CLICK → DATE_CLICK → CLICKDATA
    ├─ category_3lvl      → PRODUCT_CLICK_2
    ├─ PriceKey / NEW_PRODUCT_NAME / CATEGORY → PRICE_CHANGE
    └─ BUYER_FIO / POSITION / category        → KASPI_EMP
```

## 4. Структура данных

**Часть 1: KASPI_EMP — действующие сотрудники**
- **Источник:** `STATUS.qvd`, срез на дату «сегодня − 2 дня». Тип записи: действующий, длительное отсутствие или переходный период.
- **Связи:** по ФИО без пробелов в верхнем регистре присоединяются должность из S0008 и категория должности из Excel.
- **Назначение:** список сотрудников, в том числе тех, кто ничего не купил (охват покупками).

**Часть 2: ORDERS_FINAL — заказы (основной факт)**
- **Источник:** `BI.s43$ord_v` × `s43$orderentries_v` × `s43$prod_master_v`
- **Фильтры:** `merch_id = 92448` (Ucon store), `brand_id = 103280` (Kaspi), `ORDERDATE > 01.10.2024`
- **Гранулярность:** заказ × позиция (SKU)
- **Обогащение:**
  - покупатель: ФИО, пол, дата рождения и возраст по ИИН, должность;
  - статусы заказа;
  - отзывы и возвраты;
  - категории товара и ценовой сегмент.

**Часть 3: PRICE_CHANGE — история цен товара**
- Агрегат `ORDERS_FINAL` по полям NEW_PRODUCT_NAME × цена × CATEGORY: первая и последняя дата продажи по каждой цене и число дней между ними (`period`).
- `PriceCategory` — тип цены (правила в разделе 6).

**Часть 4: Календарь** — `ORDERDATE_CALENDAR`, все дни с 01.10.2024 по сегодня: год, месяц, день, месяц-год, день недели, неделя.

**Часть 5: Подразделения**
- `DEP_TABLE`: ИИН → `max(department_id)` из `SS_NEW.D_EMPLOYEE`, только активные записи.
- `Hierarchy`: дерево подразделений из `D_DEPARTMENT_MAIN_OLD` (путь `DEPART_PATH`, уровень `DEPART_LEVEL`).

**Часть 6: Клики (S0173.AWS_EVENTS_N, brand = 'Kaspi', с 01.09.2024)**
- **CLICKDATA:** воронка по месяцам — уникальные пользователи по событиям от клика по карточке до покупки. К ней добавляются число заказов и количество штук из `ORDERS_FINAL`.
- **PRODUCT_CLICK:** уникальные пользователи, кликнувшие по товару, по месяцам. Ключ `VIEW_KEY` = категория 2-го уровня | дата создания товара.
- **PRODUCT_CLICK_2:** уникальные пользователи, кликнувшие по категории, по месяцам.

**Часть 7: Справочник товаров** — `Каспи магазин.xlsx`, лист «Товары в магазине»: наименования, описание, признак «мужские/женские», остатки на складах. Связь с заказами по `PRODUCT_SKU`.

## 6. Бизнес-логика

### Пол покупателя

Правила применяются по порядку:

| Условие | Результат |
|---------|-----------|
| 7-я цифра ИИН — 1, 3 или 5 | Муж |
| 7-я цифра ИИН — 2, 4 или 6 | Жен |
| ФИО содержит ОВНА / ЕВНА / КЫЗЫ / ГЫЗЫ / ҚЫЗЫ | Жен |
| ФИО содержит ОВИЧ / ЕВИЧ / ОГЛЫ / УЛЫ / ҰЛЫ / ХАНАТМУХАМБЕТ | Муж |
| Иначе | Пол из `SS_NEW.D_EMPLOYEE` (F/M), иначе «Неизвестно» |

WildMatch без `*` сравнивает всю строку целиком, поэтому правила по отчеству почти не срабатывают (см. примечания).

### Дата рождения по ИИН

Первые 6 цифр ИИН — ГГММДД. Век определяется по 7-й цифре:

| 7-я цифра | Век |
|-----------|-----|
| 1, 2 | 1800 |
| 3, 4 | 1900 |
| 5, 6 | 2000 |
| Другая | 2000, если ГГ ≤ текущему году (две последние цифры), иначе 1900 |

Возраст = `Floor((сегодня − дата рождения) / 365.25)`.

### Ценовые категории (`PriceCategory`)

Правила применяются по порядку:

| Условие | Результат |
|---------|-----------|
| Цена появилась в первый день продаж товара и держалась не больше 1 дня | Стартовая цена |
| Год ≥ 2025, цена держалась меньше 21 дня и это минимальная цена товара | Акционная цена |
| Минимальная цена товара | Минимальная цена |
| Иначе | Стандартная цена |

### Воронка кликов (события S0173)

| Показатель | event_name |
|------------|------------|
| uniq_users / new_users | `shop_product_teaser_click` (new — первый клик пользователя с 01.09.2024) |
| add_cart_users | `shop_add_to_cart_click` |
| add_cartcta_users | `shop_product_cta_click` |
| buy_now_click_users | `shop_buy_now_click` |
| transaction_users | `shop_product_transaction` |

- В клики по товарам и категориям попадают только события с непустыми `created_time` и `price`.
- Название категории берётся из событий на русском языке (`ru-RU`). Категории с казахскими буквами отбрасываются.

## 7. Примечания

**Проблемы модели**
- **Синтетические ключи:**
  - `KASPI_EMP` и `ORDERS_FINAL` связаны одновременно по трём полям: `BUYER_FIO`, `POSITION`, `category`.
  - `PRICE_CHANGE` и `ORDERS_FINAL` связаны одновременно по `NEW_PRODUCT_NAME`, `CATEGORY` и `PriceKey`.
- **`PriceKey` не совпадает между таблицами:** в `ORDERS_FINAL` он строится из `category_3lvl | цена`, а в `PRICE_CHANGE` — из `CATEGORY | цена`. Счётчик AutoNumber общий, поэтому ключи сопоставляются неправильно.
- **Разные категории в `VIEW_KEY`:** в заказах используется `parent_category/category_2lvl`, в кликах — только `category_level_2`. Нужно проверить, что значения действительно совпадают. То же для связи `category_3lvl` с `PRODUCT_CLICK_2`.

**Дубли и размножение строк**
- **Должности по ФИО:** соединение идёт по ФИО. У однофамильцев с полностью одинаковыми ФИО останется одна запись (по последней дате приёма), и должность может быть чужой.
- **ФИО по ИИН:** `STATUS_MAP` строится из STATUS.qvd без фильтра по дате. На один ИИН приходится несколько строк, берётся первая.
- **Отзывы и возвраты:** если на одну позицию заказа несколько отзывов или записей о возврате, строки заказа размножаются.

**Мёртвый код**
- CTE `TT` в запросе `Hierarchy` вычисляется, но не используется.
- Карта `MAP_SECOND_MIN_PRICES` строится, но нигде не применяется.

**Мелкие ошибки**
- **Пол по отчеству:** WildMatch по отчеству без `*` (`'ОВНА'` вместо `'*ОВНА*'`) сравнивает всю строку, поэтому эти правила почти не срабатывают.
- **Подключение:** `LIB CONNECT TO 'staroks (BKS)'` стоит в середине скрипта. SQL выше него выполняются в подключении, которое было активно до этого.
- **Справочник регионов:** Жезказган и Талдыкорган повторяются; на работу маппинга это не влияет.

**Ручные файлы:** `Position ID CATEGORY.xlsx`, `Возвраты отработка.xlsx` и `Каспи магазин.xlsx` обновляются вручную. Файл категорий читается с двух разных листов (`_xlnm._FilterDatabase` и `Лист1`).

**Обновление:** полная перезагрузка, инкрементальной загрузки нет. Срез сотрудников берётся на дату «сегодня − 2 дня».
