# Показатели учета Kaspi Pay

Единый поток обращений и инцидентов Департамента Учета Kaspi Pay (ДУКП) по продуктовым направлениям: Платежи kaspi.kz, Единые взаиморасчеты, Кредиты, Карты Бизнес, Счета, Переводы.

Десять источников приводятся к одной схеме полей (`F00`–`F28`) и объединяются в одну таблицу. Для каждой записи отчёт показывает:
- тип (обращение или инцидент), тип и подтип заявки, департамент и группу продукта;
- партнёра, БИН/ИИН, ИИК, договор, сумму, автора и отдел;
- дату создания, статус и укрупнённую группу статуса;
- для заявок по задолженности — количество активных и закрытых кредитов клиента в ИБСО и РБО.

## 3. Схема связей

Таблицы объединяются через `UNION ALL`, общих ключей нет. Внутри источников:

```
Источник 1: S0108.DOCUMENTS (d)
    ├─ LEFT JOIN DOCTYPES (dt)        ON d.id_doctype = dt.id
    ├─ LEFT JOIN EMPLOYER (e)         ON d.id_author = e.id
    ├─ LEFT JOIN DEPARTMENT (dep)     ON d.id_department = dep.id
    └─ LEFT JOIN la (последнее действие по документу: ROUTETREES → ACTIONS)  ON la.id_document = d.id

Источник 2: SPB_MAIN (spb)
    ├─ JOIN SPB_SPB_ADDITIONAL_INFO (ai)  ON ai.id = spb.ID
    └─ JOIN SPB_SPB_TEXT_TEMPLATE (tt)    ON ai.template_id = tt.ID

Источники 5, 6, 7: m (документы Мотив, БИН 12 цифр)
    ├─ LEFT JOIN i (ИБСО: Z_PR_CRED_JSON → Z_CLIENT, Z_PRODUCT)   ON БИН
    └─ LEFT JOIN r (РБО: Z_BC_CRED → Z_CLIENT_JSON)               ON БИН

Источник 10: Z_KAS_DEBT_REQUEST (dr)
    ├─ LEFT JOIN Z_COM_STATUS_PRD (st)   ON C_STATUS = st.ID
    └─ JOIN da (согласующий из ДУКП: Z_OBJ_HISTORY → Z_USER → S_STAFFLIST2)  ON аудит запроса
```

## 4. Структура данных

Все части складываются в одну таблицу. Поля, неприменимые к источнику, заполняются `NULL`.

**Часть 1: Источник 1 — обращения Мотив**
- **Источник:** `S0108.DOCUMENTS`.
- **Состав:** документы разных типов (`id_doctype`), которые заведены в платежи kaspi.kz, единые взаиморасчёты, кредиты, карты бизнес, счета и спорные ситуации. Типы документов и условия отбора перечислены в `WHERE`.
- **Фильтры:** `isdeleted = 0`, нужные типы документов, а также исключение «зависших» заявок (раздел 6).
- **Признак:** `F00 = 'Обращение'`.

**Часть 2: Источник 2 — шаблон СПБ (SIEBEL)**
- **Источник:** `S0259.SPB_MAIN` + информация и шаблон из `S0015`.
- **Фильтры:** записи не удалены (`op != 'd'`), группа шаблона `spb_group_id = '2172'`.
- **Признак:** `F00 = 'Обращение'`, департамент «Департамент Поддержки Партнеров».

**Часть 3: Источник 3 — запросы АФР**
- **Источник:** `S0259.SPB_MAIN`.
- **Фильтры:** `name = 'Отдел Исполнения Запросов (УСУРП)'`, `category_name = 'Расчет задолженности, выписки'`, тип `sr_type` — `KASPIDKDKZ`, `KASPIDKDOC` или `KASPIDKOPO2`.
- **Признак:** департамент «Департамент Качества (ЗАПРОСЫ АФР)», группа продукта «Кредиты».

**Часть 4: Источник 4 — инциденты**
- **Источник:** `S0046.INCIDENT_INFO_FOR_DWH`.
- **Дедупликация:** последняя версия инцидента по `incidentid` (`ROW_NUMBER() ... ORDER BY s$change_date DESC = 1`).
- **Фильтры:** категория «Инцидент»; отдел — один из семи: Департамент Учета Kaspi Pay, Управление Учета Продуктов Kaspi Pay, Управление Учета Клиринга, Управление Сопровождения Требований, Отдел Оплаты Картотеки, Отдел Контроля Требований, Отдел Поддержки Партнеров; сервис — ИБСО, РБО, РФО, Card Suite, 1C учет, SNAP_IBSO, SNAP_RБО.
- **Признак:** `F00 = 'Инцидент'`, департамент «Департамент Учета Kaspi Pay».

**Часть 5: Источник 5 — расчёты задолженности (ДСР)**
- **Источник:** Мотив, `id_doctype = 1174`, `field2 = 'Расчеты задолженности'`, БИН (12 цифр) в `field3`.
- **Признак:** департамент «ДСР», группа «Кредиты». К каждой записи добавляются количество активных и закрытых кредитов клиента в ИБСО и РБО.

**Часть 6: Источник 6 — расчёт задолженности (РЗ, Debt Collection)**
- **Источник:** Мотив, `id_doctype = 931`, `field1 = 'Запросы по платежкам'`, `field7 = 'ЮЛ'`, БИН в `field2`.
- **Дополнительный фильтр:** текст `field4` содержит «расчет … задолжен».
- **Признак:** департамент «Debt Collection Business», группа «Кредиты», кредиты ИБСО и РБО.

**Часть 7: Источник 7 — платёжки (Debt Collection)**
- **Источник:** те же документы, что в источнике 6, но без фильтра по тексту.
- **Признак:** тип «Предоставление платежных документов по выдаче кредита», подтип «Запросы по платежкам», кредиты ИБСО и РБО.

**Часть 8: Источник 8 — госпошлина Бизнес Кредит (БК)**
- **Источник:** `S06.Z_KAS_REQUEST_PAY`, `C_VID_PLAT = '76781828737'`, JSON `AFTER_BODY`.
- **Фильтры:** запись не удалена, статус из списка (оплачено, `ISNULL` и 14 статусов рассмотрения).
- **Признак:** департамент «Debt Collection Business», группа «Кредиты».

**Часть 9: Источник 9 — госпошлина Единые взаиморасчёты (ЕР)**
- То же, что источник 8, но `C_VID_PLAT = '163199699211'`, группа «Единые взаиморасчеты».

**Часть 10: Источник 10 — справка о наличии ссудной задолженности**
- **Источник:** `S06.Z_KAS_DEBT_REQUEST`.
- **Фильтр:** в отчёт попадают только запросы, по которым есть действие сотрудника «Департамент Учета Kaspi Pay» в журнале изменений (причина «ИБСО», «ИБСО-КБ» или «Показать суммы»), сделанное в период его работы в этой должности.
- **Признак:** подтип «Запрос справки», департамент «Департамент Поддержки Партнеров», группа «Кредиты».

### Группа инцидента (`F07`, источник 4)
Определяется по типу инцидента (`incindenttype`): Взаиморасчеты, Кредиты и гашение, Картотека и аресты, Счета, Авторизация и доступ, Отчетность, Документы и проводки, Карты и Kaspi Gold, Клиенты; всё остальное — «Прочее».

### Исключение «зависших» заявок (источник 1)
Исключаются заявки Мотива в статусе `state = 4` и `isrejected = 0`, у которых по журналу действий последнее действие:
- сделано самим автором (самозакрытие / архивация), или
- содержит «доработ» и сделано не автором (вернули на доработку без дальнейшего движения).

Правило применяется ко всем типам документов источника 1. Принято сознательно: возвраты «на доработку» по типу 868 часто делает «Управление Учета Клиринга» (подразделение ДУКП), и такие заявки тоже исключаются.

### Укрупнённый статус (`Статус заявки`)

| Источник | Правило |
|----------|---------|
| 1, 5, 6, 7 (Мотив) | `state = 4` → Закрыта; `state = 0` и `isrejected = 0` → В работе; `state = 0` и `isrejected` 1 или 2 → Отклонена; иначе Прочее |
| 2, 3 (СПБ) | «Готово» → Закрыта; «В работе», «Передано в СПБ» → В работе; иначе Прочее |
| 4 (инциденты) | «Закрыто», «Выполнено» → Закрыта; «В работе», «Зарегистрирован», «Запрошено доп. инфо», «Прикреплен к родительскому инциденту» → В работе; «Отменен» → Отклонена; иначе Прочее |
| 8, 9 (госпошлина) | `PAID` → Оплачено; один из 14 статусов рассмотрения (согласования, контроль, `IN_WORK_*`, `WAIT_BILL`, `FOR_PAYMENT`, `VOZV_INIT`, `CREATE_PAY`) → В работе; иначе (в том числе `ISNULL`) → Не оплачено |
| 10 (справка) | Статусы `2723434641`, `2260505535` → Исполнена; `26398878080` → Возвращена без исполнения; иначе В работе |

### Кредиты клиента (источники 5–7)
- Клиент находится по БИН (12 цифр, нецифровые символы убираются).
- **ИБСО:** договоры класса `KRED_CORP`; активный — без даты закрытия.
- **РБО:** договоры `Z_BC_CRED`; активный — без даты закрытия или со значением `None`.
- Если клиента нет в системе, значения равны 0.

### Согласующий из ДУКП (источник 10)
В журнале изменений запроса ищутся действия с причиной «ИБСО», «ИБСО-КБ» или «Показать суммы». Действие должно быть сделано сотрудником «Департамент Учета Kaspi Pay» в период его работы в этой должности (от последнего назначения или приёма до увольнения). Если таких сотрудников несколько, выбирается один — по `MAX` от ФИО.

## 7. Примечания

**Возможные дубли и пересечения**
- **Один документ может попасть в три источника.** Документы типа 931 с `field1 = 'Запросы по платежкам'` и `field7 = 'ЮЛ'` входят в источник 1, а также в 7 и (при подходящем тексте) в 6. В источнике 1 они относятся к «Единым взаиморасчётам», в источниках 6 и 7 — к «Кредитам». Пересечение 6 и 7 задумано автором, пересечение с источником 1 в заметках не упоминалось. Для подсчёта обращений по уникальным документам нужно учитывать `F03` и `F07`.
- **Правило исключения «зависших» заявок действует только в источнике 1.** Те же документы в источниках 5, 6 и 7 не фильтруются.
- **Возможное лишнее исключение в правиле «зависших» заявок.** Если у закрытого документа (`state = 4`, `isrejected = 0`) нет записей в журнале действий, поля последнего действия пусты, условие в `NOT (...)` даёт `NULL`, и строка отбрасывается. Получается, что исключаются не только самозакрытые и возвращённые заявки, но и закрытые без журнала действий. Нужно проверить, есть ли такие документы.
- **Нет дедупликации в источниках 2, 3, 8, 9, 10.** Источник 4 берёт последнюю версию по `s$change_date`, а в остальных используется только фильтр удаления (`op != 'd'`, `S$OP_TYPE != 'D'`). Если в таблицах хранится история изменений записи, одна заявка попадёт в отчёт несколько раз.

**Согласованность значений**
- **Разный словарь статусов.** Поле `Статус заявки` принимает значения «Закрыта / В работе / Отклонена / Прочее», «Оплачено / В работе / Не оплачено» и «Исполнена / Возвращена без исполнения / В работе». Для общих срезов статусы нужно приводить к одному словарю.
- **Разные типы дат.** В источниках 8 и 9 дата создания берётся из JSON как строка, в остальных — как дата-время. При `UNION ALL` типы приводятся к общему, и `F18` в Qlik может стать текстом. Нужно проверить, что дата распознаётся как дата.
- **Смысл полей зависит от источника.** `F08 Партнер` для инцидентов — это инициатор (ФИО), а не партнёр. `F21 Автор` для справки — это согласующий из ДУКП, а не автор.
- **Подозрительное написание.** Сервис `'SNAP_RБО'` в источнике 4 записан со смешением латиницы и кириллицы (`R` латинская, `БО` кириллические). Если в источнике значение пишется латиницей, такие инциденты не попадут в выборку.
- **Одна запись в двух списках.** Тип инцидента «Ошибка при печати выписки» входит и в «Счета», и в «Документы и проводки». Срабатывает первый вариант («Счета»), второй не используется.
- **Кредиты без продукта считаются активными.** В подсчёте ИБСО `LEFT JOIN Z_PRODUCT` без записи продукта даёт пустую дату закрытия, и договор попадает в активные.
- **Источник 10 ограничен сотрудниками ДУКП.** `INNER JOIN` с журналом оставляет только запросы, к которым прикасался сотрудник «Департамент Учета Kaspi Pay». Запросы без таких действий в отчёт не попадают.

**Прочее**
- Большое число условий по типам документов Мотива (`id_doctype`) зашито в запрос. При появлении новых типов документов их нужно добавлять в несколько `CASE` и в `WHERE`.
- Год в `Месяц создания` задан константой 2026 (используется только для названия месяца, на значение не влияет).
- **Обновление:** полная перезагрузка при каждом reload.
